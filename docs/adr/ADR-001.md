# ADR-001: Выбор паттерна Event Sourcing для модуля «Журнал посещений»

## Статус
**Принято** (Accepted)

## Дата принятия решения
22 октября 2026 г.

## Контекст и проблема

Модуль журнала посещений АИС «Система бюро пропусков (СКУД)» должен фиксировать каждое событие прохода сотрудника или посетителя через турникет:
- вход / выход;
- время события;
- точка контроля;
- результат фейсконтроля.

К системе предъявляются следующие требования:

1. **Полный аудит** — возможность восстановить состояние журнала на любой момент времени.
2. **Неизменяемость истории** — невозможность удаления или изменения записей задним числом (требование службы безопасности).
3. **Высокая частота событий** — до 500 проходов в минуту в часы пик.

Традиционный подход с CRUD-таблицей, где запись обновляется при изменении статуса пропуска, **не удовлетворяет** требованиям аудита и неизменяемости истории.

## Принятое решение

Применить **паттерн Event Sourcing** для модуля журнала посещений.

Каждое событие прохода (например, `VisitorEntered`, `VisitorExited`, `AccessDeniedByFaceRecognition`) сохраняется как **неизменяемая запись** в таблице событий `access_events` со следующими полями:

| Поле | Назначение |
|---|---|
| `event_id` | Уникальный идентификатор события (UUID) |
| `aggregate_id` | ID пропуска |
| `event_type` | Тип события |
| `payload` | JSON с данными события |
| `occurred_at` | Временная метка |
| `version` | Версия схемы события |

Текущее состояние журнала строится путём применения (**replay**) всех событий с начала периода. Для ускорения чтения используется **проекция (read model)** в отдельную таблицу `access_log_current`.

## Отклонённая альтернатива и причина

Рассматривался **традиционный подход CRUD** с одной таблицей `access_log` и флагом `is_active`, где при выходе посетителя запись обновлялась.

Отклонён по следующим причинам:

1. **Нарушает требование неизменяемости** — запись можно случайно изменить или удалить, что недопустимо для системы безопасности.
2. **Невозможно восстановить историю** — нельзя узнать, кто и когда изменил срок действия пропуска.
3. **Проблемы производительности** — при высокой нагрузке `UPDATE`-операции создают блокировки строк, тогда как Event Sourcing использует только `INSERT`, что обеспечивает лучшую производительность при записи.

## Последствия решения

### Положительные
- Полный аудит-трейл всех событий прохода.
- Соответствие требованиям службы безопасности (неизменяемость истории).
- Масштабируемость записи за счёт использования только `INSERT`-операций.
- Возможность восстановления состояния системы на любой момент времени.

### Отрицательные
- Усложнение логики чтения — необходима реализация проекции (read model).
- Увеличение объёма хранилища событий.
- Необходимость разработки механизма **replay** при миграциях схемы событий.

### Технические задачи, вытекающие из решения
1. Реализовать механизм **снапшотов** для оптимизации replay при большом количестве событий.
2. Настроить индексацию таблицы `access_events` по полям `aggregate_id` и `occurred_at`.
3. Обеспечить идемпотентность обработки входящих событий от турникетов.
4. Разработать механизм версионирования схемы событий (`version`).

## Связанные артефакты
- Карточка дефекта `DEF-042` (дублирование записей при повторном срабатывании турникета) — частично решается идемпотентностью событий.
- OpenAPI-спецификация эндпоинта `POST /api/v1/visitor-passes` — контракт создания пропуска должен учитывать событийную модель.
